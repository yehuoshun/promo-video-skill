# DeepSeek 执行规范

本文件规定 DeepSeek 在本项目中执行宣传片任务时的工作方式。目标是让模型按可检查的合同推进，而不是凭“看起来合理”直接交付。

## 每轮工作顺序

1. 读取项目根目录的 `AGENTS.md`。
2. 判断当前处于哪个阶段，只读取该阶段需要的一份 `references/` 文档。
3. 列出本轮的输入文件、允许修改的文件和出口条件。
4. 先修改数据文件，再修改场景或脚本。
5. 运行本阶段对应的检查命令。
6. 检查失败时只处理当前失败项，修复后重新运行命令。
7. 未通过出口条件时，不进入下一阶段。
8. 输出本轮结果：完成项、修改文件、检查命令、检查结果、未解决问题、下一步。

## 输入输出合同

每个场景必须能回答四个问题：

- 这个场景的 `purpose` 是什么？
- 观众要理解什么 `claim`？
- 画面证据在哪里？
- 证据不可用时如何 `fallback`？

`purpose` 只允许：`hook`、`problem`、`solution`、`proof`、`emotion`、`cta`。

`proof` 场景必须有真实素材和来源 URL。没有证据时，必须缩短、删除或改成明确标注的示意图，不得自行补写事实。

## 禁止行为

- 不猜产品事实、数字、排名、功能和授权状态。
- 不把搜索摘要当作事实来源；必须记录可访问的官方页面或原帖。
- 不在素材不足时生成一张看似真实的产品截图。
- 不为了凑时长重复镜头或用无关特效填空。
- 不在场景组件里写死时间和屏幕文案。
- 不在 `timing.json` 之外另写字幕时间。
- 不把“已经渲染”说成“已经审图”。
- 不把 WARN 说成通过。
- 不修改允许文件范围以外的文件。

## 失败处理

失败报告必须指向具体场景、字段、文件或命令。例如：

```text
ERROR showcase-02:
purpose=proof，但 evidence 为空。
请补充真实截图和 source，或把 purpose 改为 emotion。
```

不要只写“质量不够”“感觉不自然”“请优化”。如果问题无法自动判定，标记为“待人工审片”，并说明需要看哪一帧或听哪一段。

## 每轮交付格式

```markdown
## 已完成

## 修改文件

## 检查命令

## 检查结果

## 未解决问题

## 下一步
```

## 交付前的分工

DeepSeek 负责完成调研、分镜、代码、渲染和可自动检查的修复。人只在以下位置做判断：

- 需求确认和风格样帧选择
- 静帧拼图审查
- 成片试听和最终审美判断
- 私有页面、内部素材和版权风险确认

没有完成静帧审查和 `scripts-win\\verify.cmd`，不得称为交付。
